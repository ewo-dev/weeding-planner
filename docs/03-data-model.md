# Plan de Table — Data Model

## 1. Purpose

This document defines the canonical data model used by the application.

It is the single source of truth for:

* Entity names and fields.
* Type definitions (TypeScript).
* Validation rules.
* The serialized shape stored locally and in exported project files.
* Migration strategy when the schema evolves.

The engine (`04-seating-engine.md`) and repository (`05-persistence.md`) consume this model.

---

## 2. Overview

The application revolves around one aggregate: the **Plan**.

A plan contains:

* **Tables** — physical tables with capacity and position.
* **Guests** — the people to seat.
* **Constraints** — relationships between guests.
* **Assignments** — which guest sits at which table (and which seat).

```text
Plan
  ├── meta          (id, name, createdAt, updatedAt, schemaVersion)
  ├── tables[]      (Table)
  ├── guests[]      (Guest)
  ├── constraints[] (Constraint)
  └── assignments[] (Assignment)
```

All entities use string IDs generated by `crypto.randomUUID()`.

---

## 3. TypeScript Definitions

The model lives in `lib/schema/plan.ts` and is exported via `types/plan.ts`.

```ts
// ---------- Meta ----------

export interface PlanMeta {
  id: string
  name: string
  createdAt: string         // ISO-8601
  updatedAt: string         // ISO-8601
  schemaVersion: number     // for migrations
}

// ---------- Tables ----------

export type TableShape = 'round' | 'rectangle'

export interface TablePosition {
  x: number                 // workspace coordinate (px)
  y: number
}

export interface Table {
  id: string
  name: string              // "Table 1", or user-renamed
  shape: TableShape
  capacity: number          // max seats
  position: TablePosition
}

// ---------- Guests ----------

export interface Guest {
  id: string
  name: string
  group?: string            // optional, free-form label
  notes?: string
}

// ---------- Constraints ----------

export type ConstraintKind =
  | 'must_together'    // mandatory: A and B at the same table
  | 'prefer_together'  // soft preference
  | 'must_not_together'// mandatory separation

export interface Constraint {
  id: string
  kind: ConstraintKind
  a: string              // guest id
  b: string              // guest id
}

// ---------- Assignments ----------

export interface Assignment {
  guestId: string
  tableId: string
  seatIndex: number      // 0..capacity-1
}

// ---------- Plan ----------

export interface Plan {
  meta: PlanMeta
  tables: Table[]
  guests: Guest[]
  constraints: Constraint[]
  assignments: Assignment[]
}
```

## 4. Entities in Detail

### 4.1 Plan

| Field          | Type      | Notes                                       |
| -------------- | --------- | ------------------------------------------- |
| `meta.id`      | string    | UUID, primary identity.                     |
| `meta.name`    | string    | Defaults to "Untitled plan".                |
| `meta.createdAt` | string  | ISO-8601, set once at creation.             |
| `meta.updatedAt` | string  | ISO-8601, refreshed on every save.         |
| `meta.schemaVersion` | int | Current: `1`. Used for migrations.       |

Invariants:

* `meta.schemaVersion` is always present.
* `meta.updatedAt >= meta.createdAt`.

### 4.2 Table

| Field      | Type      | Notes                                       |
| ---------- | --------- | ------------------------------------------- |
| `id`       | string    | UUID.                                       |
| `name`     | string    | 1-40 chars, trimmed, unique within the plan.|
| `shape`    | enum      | `round` or `rectangle`. Extensible.         |
| `capacity` | number    | Integer, 1-20 for MVP.                      |
| `position` | object    | `{ x, y }` workspace coordinates.           |

Invariants:

* `capacity >= 1`.
* A guest can only be assigned to a seat `< capacity`.
* Table IDs must be unique within a plan.
* Table names should be unique; the UI disambiguates on conflict.

### 4.3 Guest

| Field   | Type   | Notes                                          |
| ------- | ------ | ---------------------------------------------- |
| `id`    | string | UUID.                                          |
| `name`  | string | 1-80 chars, trimmed, required.                 |
| `group` | string | Optional, free-form label (e.g. "Family").     |
| `notes` | string | Optional, free-form.                           |

Invariants:

* Names should be unique within a plan (the UI warns on duplicates, doesn't block).
* Guest IDs must be unique.

### 4.4 Constraint

| Field  | Type     | Notes                                          |
| ------ | -------- | ---------------------------------------------- |
| `id`   | string   | UUID.                                          |
| `kind` | enum     | `must_together` / `prefer_together` / `must_not_together`. |
| `a`    | string   | Guest id.                                      |
| `b`    | string   | Guest id.                                      |

Invariants:

* `a !== b` (a guest cannot constrain themselves).
* `(a, b)` and `(b, a)` are equivalent — the model stores the unordered pair.
  At the persistence boundary, sort `(a, b)` lexicographically to canonicalize.
* At most one constraint per (unordered) pair, per kind.
  Two guests cannot have both `must_together` and `must_not_together`.

### 4.5 Assignment

| Field       | Type   | Notes                                          |
| ----------- | ------ | ---------------------------------------------- |
| `guestId`   | string | UUID.                                          |
| `tableId`   | string | UUID.                                          |
| `seatIndex` | number | Integer, `0 <= seatIndex < capacity`.          |

Invariants:

* Each guest has at most one assignment.
* Each `(tableId, seatIndex)` slot holds at most one guest.
* `seatIndex` is contiguous per table from `0` to `capacity - 1`.
* An assignment references an existing `tableId` and `guestId`.

Assignments live inside the plan. They are intentionally separate from `Table` and `Guest` to keep entities flat and to make serialization trivial.

## 5. Derived Data (not stored)

These are computed from the plan and never persisted:

* **Plan statistics** — totals, seated/unseated counts, conflicts.
* **Generation report** — produced by the seating engine.
* **Guest seating status** — derived from `assignments`.

Selectors live in `lib/plan/selectors.ts`.

---

## 6. Validation

All reads and writes go through `zod` schemas in `lib/schema/plan.ts`:

* `PlanSchema` — validates the entire plan.
* `GuestSchema`, `TableSchema`, etc. — validate individual entities on input.
* Partial schemas for form input (e.g. `GuestDraftSchema` accepts optional fields).

Validation happens at:

1. **Repository load/import** — reject corrupted local plans or project files with a typed error.
2. **Action dispatch** — actions accept plain objects and validate before reducing.
3. **Form submit** — client-side before the reducer sees the value.

The engine never trusts its inputs. It re-validates internally.

## 7. Serialization

### IndexedDB shape

IndexedDB stores plans as structured records in one database:

```text
database: weeding-planner
store: plans        -> Plan, keyed by meta.id
store: preferences  -> active plan id and non-plan UI preferences
```

The repository owns transactions and indexes. The plan record is the canonical local copy; summaries may be indexed or derived without duplicating plan data.

### JSON project-file shape

Exported files use a versioned envelope so the file format can evolve independently from the browser database:

```json
{
  "format": "plan-de-table-project",
  "formatVersion": 1,
  "exportedAt": "2026-09-21T10:42:11.000Z",
  "plan": { "meta": {}, "tables": [], "guests": [], "constraints": [], "assignments": [] }
}
```

Import must validate the envelope, migrate supported older format versions, then validate and persist the contained plan. Unknown future versions must be rejected without overwriting existing data.

## 8. Invariants Summary

Hard invariants enforced by validation:

1. `Plan.meta.schemaVersion === CURRENT_VERSION` after migration.
2. `Table.id`, `Guest.id`, `Constraint.id` are unique within the plan.
3. `Table.name` is unique within the plan.
4. `Constraint.a !== Constraint.b`.
5. No `(a, b)` pair has both `must_together` and `must_not_together`.
6. Every assignment references an existing table and guest.
7. `0 <= seatIndex < capacity` for every assignment.
8. No two assignments share the same `(tableId, seatIndex)`.
9. No two assignments share the same `guestId`.

Soft invariants enforced by the UI but not blocking:

* Guest names unique.
* All mandatory constraints satisfiable given current capacity.

## 9. Schema Versioning & Migrations

The model ships with `CURRENT_VERSION = 1`.

When a breaking change is needed:

1. Bump `CURRENT_VERSION`.
2. Add a migration function in `lib/schema/migrations.ts`:

```ts
type Migration = (raw: unknown) => unknown

const migrations: Record<number, Migration> = {
  1: (raw) => raw,    // identity
  // 2: (raw) => { ... },
}
```

3. On repository load, run migrations sequentially from the stored `meta.schemaVersion` up to `CURRENT_VERSION`.
4. After migration, re-validate. If validation fails, surface a "Plan could not be loaded" error and offer a reset.

Migrations are forward-only. Backwards compatibility within a deployed version window is acceptable.

## 11. Open Model Questions

Tracked for future iteration:

1. **Guest groups** — should `group` be a first-class entity (id + label) or stay free-form? MVP: free-form.
2. **Plus-ones** — a guest bringing an unnamed companion. MVP: model as a separate `Guest` with name "+1 of Alice".
3. **Multiple events** — a plan could represent rehearsal + ceremony + reception. MVP: one plan = one event.
4. **Custom shapes** — beyond round/rectangle. The `TableShape` enum is the extension point.
